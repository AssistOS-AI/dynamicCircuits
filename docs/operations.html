Evidence, reuse, and large inputs

Receipts bind results to inputs, code, policy, and dependencies. Epochs and semantic cache keys control reuse. Registry layers organize large knowledge bases, and capability brokers mediate external effects.

Why this page exists

This page explains how Dynamic Circuits stores execution evidence and how that evidence remains valid when work is cached, split across large documents, or performed through external capabilities. It follows the runtime and assurance layers: the runtime creates node and circuit evidence, assurance adds closure and policy evidence, and operations persists, reuses, and protects those records.

The current runtime implements deterministic in-memory node and circuit receipts. Persistent receipts, semantic caches, epochs, large-document registries, capability brokers, and signatures are planned components defined by the linked DS files.

Five terms used below

A new reader needs five definitions before following the storage design. A receipt is the structured record of one execution. A digest is a content hash used to identify exact bytes or canonical values. An epoch names one stable snapshot of sources, packages, registry, and policy. A cache key identifies the complete conditions under which an old computation may be reused. A capability is an explicit, limited permission to perform an external operation such as reading one artifact or calling one allowlisted service.

Only the first two are substantially visible in the current runtime. Epochs, persistent semantic cache, registry-wide evidence, and mediated effect capabilities describe later milestones. The page keeps them together because they determine whether a stored result still means the same thing after inputs, code, policy, or external state changes.

Receipt hierarchy

The hierarchy diagram shows aggregation. A node receipt describes one command or child-circuit call. A circuit receipt binds the ordered interface, required node receipts, checks, and outputs. A closure receipt adds matcher coverage and fixed- point rounds. The final receipt adds task sources, attempt lineage, goals, trust decisions, conflicts, budgets, and publication status.

The evidence-input diagram shows why the final receipt is more than an execution log. Source and artifact commitments identify the evidence bytes. Profile and epoch identify the rules, registry snapshot, and resource policy. Goals and trust identify which propositions were checked and which implementations were accepted. Changing any of these inputs creates a different final identity.

Node receipts bind code, canonical inputs and outputs, checks, effects, capabilities, artifacts, oracle calls, state, and dependencies. Circuit receipts add interface bindings, relevant slice, invariants, child instances, and public outputs. Closure receipts bind registry coverage and every fixed-point round. Final receipts bind sources, attempts, goals, trust decisions, conflicts, budgets, and acceptance gates. Canonical serialization, content hashes, signatures, selective disclosure, replay modes, and audit queries are specified in DS019.

In the current Eval 1 run, the root receipt contains the eval1.analysis execution and three child receipts for kb.policy. Each child records hashed inputs, the local node outcome, and its returned finding. The committed results/runtime-result.md is rendered directly from the public outputs and receipt. Evaluation expectations live outside input/ and never replace the observed executor report. Run the command in the manual tutorial to print and inspect that receipt directly.

Cache and epochs

A cache key includes command/code/package digests, canonical inputs, dependency lock, declared environment, profile-sensitive semantics, runtime version, and epoch-bound external state. A hit revalidates the old receipt and emits a new reuse receipt; it never upgrades trust. Epochs snapshot sources, registry, matchers, templates, profile, and external versions. Incremental invalidation follows semantic dependencies and must converge to the same strict fixed point as a full run. See DS020.

Example: changing one chapter changes that artifact digest and invalidates its interpretation circuit, dependent facts, matching decisions, synthesis nodes, and final receipt. Interpretations for unchanged chapters remain reusable when their package, profile, runtime, and epoch dependencies still match. The reuse receipt records the original result instead of presenting the value as a fresh execution.

Large knowledge bases and documents

The registry separates a compact catalog, structured metadata indexes, optional similarity retrieval, full manifests, and content-addressed stores. Strict matching is enumerable within receipt-bound shards. Large documents are immutable artifacts segmented by stable locators; section circuits publish provenance-linked facts and summaries; cross-section circuits reconcile terminology, timelines, claims, and citations. Pure work may run in parallel or distributed leases with deterministic aggregation. Approximate and strict coverage are always reported separately. See DS021.

For a book-sized source, each chapter can publish dates, definitions, claims, and citations with stable section locators. Cross-section circuits consume those structured outputs to find inconsistent terminology or timelines. This preserves the source span behind every global conclusion while avoiding repeated processing of unchanged raw chapters.

Current behavior is simpler: the CLI hashes every regular input file, and Codex decides how to inspect it with locally available tools. There is no automatic chapter segmenter or persistent artifact store yet. For a current manual test, split large text at meaningful headings, keep stable source labels, and require the report to list unsupported files. The input guide gives concrete preparation rules.

Effects and threat boundary

The full architecture declares effects and supplies least-authority capabilities through host brokers: opaque artifact handles, allowlisted network requests, injected time/randomness, secret references, and receipt-bearing oracles. Resource budgets cover time, memory, output, logs, regexes, recursion, closure growth, calls, bytes, and cost. Package locks, signatures, SBOMs, revocation, redaction, and tenant isolation complete the operational boundary.

The present Node VM removes ambient process and I/O capabilities and normalizes cross-realm values. Hostile multi-tenant execution additionally requires process isolation, memory and CPU quotas, syscall restrictions, and transactional effect brokers. The full threat model and current learning-workspace limitation are in DS008.

Example: a future network-enabled command would receive an allowlisted broker capability, not the ambient Node network API. The broker would validate the destination and request size, enforce budgets, materialize the response as an artifact, and add the request and response commitments to the receipt.

Read SOP runtime first for the receipt fields produced today, then coverage and acceptance for the planned evidence added above a successful graph. The normative storage, cache, and scalability contracts are DS019, DS020, and DS021.
