Mandatory rules and closure

A reviewed matcher marks when a reusable KB circuit is compulsory. The runtime discovers every binding produced by the loaded mandatory matcher registry, executes each target, indexes any newly published facts, and repeats until no new instance exists.

The problem this feature solves

A coding agent can inspect many KB packages, but a final result must not depend on whether it remembered every relevant call. Dynamic Circuits therefore separates three responsibilities. Task SOP publishes current facts under explicit semantic keys. Reviewed KB matchers decide which published values bind to a rule. The executor enumerates and runs the complete discovered instance set.

The guarantee has a precise boundary: it covers all instances returned by every reviewed kb.* mandatory matcher loaded for the run. It does not claim that an absent matcher exists, that unrestricted prose was interpreted perfectly, or that the registry is trusted by an external authority. Exact publication keys and reviewed matcher code make the implemented claim testable.

The task-facts node contains values extracted from current input. publish registers one immutable value, semantic key, provenance label, and stable handle. The matcher reads the index and returns handle tuples. A tuple activates the named target; an empty matcher result means that matcher has no current instance and the executor invents nothing.

The source convention

The mandatory marker belongs on a small, reviewed matcher package—not on the target rule. This lets a generic target remain reusable and makes applicability independently testable. Trigger keys are dotted identifiers such as order.raw; the compiler requires the matcher to select exactly its declared trigger keys.

@template mandatory
@trigger "order.raw"
@apply kb.order.normalize
@input index delta
@output matches
@entries select $index "order.raw"
@matches bind $entries

@template mandatory places this reviewed kb.* package in the automatic registry. @trigger declares the semantic family that can activate it. @apply names an existing circuit whose input arity must match every returned tuple. The fixed two-input matcher interface receives a deterministic index snapshot and the newest publications; its single output is the complete tuple list.

Mandatory matchers cannot contain local JavaScript. They use the restricted deterministic commands select, bind, join, distinct, concat, and emptyList. A one-key matcher selects publications and wraps each handle in a one-element tuple. A two-key matcher may join two selected sets by equal JSON-pointer fields before deduplication.

What task circuits publish

@order task.orders
@rawPublication publish $order "order.raw" "orders.md#OA-1"

The first call reads a value from a task-local package generated from human input. The second call exposes that value to matching. It does not invoke normalization, approval, or currency policy. The coding agent must publish a key only when the input really provides the corresponding fact shape; semantic publication is an explicit interpretation decision recorded in task SOP.

Every raw-order handle creates one normalization instance. Successful normalization returns both a value and a new order.normalized publication. That publication activates two different reviewed matchers, so each order creates an approval instance and a currency instance. With two raw orders, the expected fixed point contains two normalization plus four assessment instances.

How the executor proves closure

  1. Execute the no-input root task.analysis and index every semantic publication in its public outputs.
  2. Load all compiled mandatory matcher packages under the kb. namespace in stable name order.
  3. Run active matchers, validate handle tuples and target arity, deduplicate instance identities, and execute every new target instance.
  4. Index publications returned by successful targets and repeat matching with the enlarged fact set.
  5. Recompute the expected instance set and compare it with the executed set. Success requires zero missing instances.

The closure receipt contains the matcher-registry hash, registry size, semantic keys, rounds, publication count, expected identities, executed identities, missing identities, failure evidence, and its own hash. The executor report also renders each automatically applied target's actual public outputs. A policy finding may say compliant: false while execution remains successful; refusal, rejection, error, or an exhausted budget prevents a successful closure claim.
