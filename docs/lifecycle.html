What happens during one analysis

This page follows the notice-policy example from files placed in a task folder to generated SOP, runtime findings, and the final report. It marks each step as current behavior or planned assurance work.

Start with three readable files

The user creates work/notice-review/input/. The folder contains rule.md with the ordinary and exceptional notice periods, cases.md with one row per case, and task.md with the requested fields and coverage requirement. The user also supplies a KB path, even when that KB currently has no reviewed circuit.

node src/cli.mjs \
  -kbdir ./kb \
  -workdir ./work/notice-review \
  -agent codex

The presence of -workdir selects analysis mode. The process runs with the task folder as its current directory. The task is writable; reviewed KB circuits are readable and remain outside the task's write area.

The CLI prepares the folder

flowchart LR
      I[input files] --> M[hash manifest]
      M --> W[sop and results folders]
      W --> A[Codex workspace]

The CLI recursively inventories regular files under input/. For each file it records the relative path, byte size, and SHA-256 digest in .dynamic-circuits/input-manifest.json. It creates missing sop/ and results/ folders, writes managed instructions when no user-owned guidance exists, and links the project circuitSkills catalog for Codex discovery. It then starts Codex in that prepared directory.

Codex turns prose into SOP

Codex must account for every manifest entry. It reads the policy, cases, and requested output; inspects reusable package interfaces under kb/circuits/; and writes task code under sop/. For the notice example, a useful implementation separates:

  • a rule circuit that accepts one case and selects either the 30-day minimum or the 10-day exception;
  • a task circuit that supplies the interpreted case rows, calls the rule once per case, aggregates findings, and checks coverage.

The source documents remain unchanged. SOP is the agent's reviewable interpretation of them. A reviewer can therefore detect a missing exception, a transcribed value, or a case that was never wired before trusting the prose report.

Local code checks and runs SOP

flowchart LR
      S[generated SOP] --> C[compile]
      C --> X[execute]
      X --> R[outputs and receipt]

The parser reads directives and local JavaScript command bodies. The compiler derives package names from file paths, resolves child calls, validates ordered arguments and immutable wires, rejects graph cycles, and identifies nodes required by outputs and goals. Only a valid graph reaches the runtime.

The runtime executes required nodes in dependency order. In the committed example it calls the rule three times, produces three findings, calculates totals, and checks that every case was classified. A command can succeed, refuse an invalid input, fail its own check, or raise an execution error. The root outcome exposes no successful-looking output when a required child fails.

The report is grounded in execution

Codex writes reader-facing material under results/. A useful report names all input files, explains the policy interpretation, lists the circuits compiled and run, states each runtime outcome, reports uncovered material, and distinguishes limitations from conclusions. The receipt supplies machine evidence: package hashes, node states, input and output hashes, child receipts, goal results, and public outputs.

For the committed notice case, the report says case A violates the ordinary minimum, case B satisfies the documented exception, and case C satisfies the ordinary minimum. It can point to a successful receipt and a passing three-case coverage goal. It must not claim that an unknown external law or an absent KB rule was checked.

What the planned assurance stage adds

flowchart LR
      F[published case facts] --> M[match all rules]
      M --> E[execute expected instances]
      E --> P[accept or explain gap]

Today Codex selects the explicit rule calls and a human reviews coverage. The planned semantic registry will query all rule packages that consume notice-case facts. Deterministic matchers will decide whether the ordinary rule and exception apply to each case. Mandatory closure will execute newly expected instances until no new facts activate more rules. An audit will then compare expected instance keys with executed receipt keys.

If the exception matched case B but its circuit never ran, the future system will report incomplete coverage. If the consent fact is missing, it will report INCONCLUSIVE rather than assume consent is false. Only after coverage, goals, trust, conflicts, budgets, and receipt completeness pass may a strict profile publish ACCEPTED. The details are expanded with the same example on the coverage page.

Learning uses a different destination

Running with only -kbdir ./kb selects learning mode. Codex reads documents under kb/input/ and reviewed packages under kb/circuits/, then writes proposed reusable packages under kb/candidates/. It does not write a task sop/ folder and does not promote its own proposal to the trusted circuit set. The candidate needs provenance, applicability, explicit ports, refusal behavior, and tests before a separate review can promote it.

Analysis therefore answers one task in a workdir; learning proposes code for future tasks in the KB. Both use the same parser, compiler, runtime, skills, and coding-agent adapter. The manual tutorial contains runnable commands for both flows.
