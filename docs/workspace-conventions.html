Documentation / KB and task convention

Keep reusable knowledge separate from the current task

Every analysis uses two explicit workspaces. The knowledge base stores rules, reference material, and reviewed circuits that may be reused. The task workspace stores only the current request, its case data, the SOP written for that request, and its results. Evaluation fixtures use the same names: kb/ and task/.

The decision to make before adding a file

Classify a file by its intended lifetime, not by its extension. Put a document in the KB when it defines knowledge that should remain applicable after the current analysis finishes: a policy, terminology guide, interpretation rule, or reference corpus. Put a document in the task when it identifies the current cases, observations, chapters, questions, requested output, or acceptance criteria. A Markdown policy and a Markdown case list are both readable text, but they belong to different workspaces because one is reusable and the other describes this run.

If the file contains…Place it in…Reason
A reusable rule, policy, glossary, or reference documentkb/input/It is source knowledge that a learning run may interpret and package for later tasks.
A reviewed reusable SOP packagekb/circuits/Analysis may load it as trusted executable knowledge without rewriting it.
The current cases, dataset, chapters, questions, or requested deliverabletask/input/It defines this analysis and should not silently become permanent knowledge.
SOP that adapts KB knowledge to the current inputtask/sop/It is an executable interpretation owned by this task.
Reports, findings, receipts, or checked summariestask/results/They are outputs and must never be rediscovered as new source input.

The table is also a review rule. If a case table appears in kb/input/, reviewers should ask whether those observations are genuinely reusable reference data. If a general policy appears in task/input/, reviewers should ask whether later tasks need the same rule and whether it should instead enter the KB learning and promotion process described in the CLI workspace guide.

The left-to-right connection is deliberately one-way. During analysis, the agent may inspect and call reviewed KB circuits, but it must not edit them. It combines those circuits with the current input in task/sop/ and publishes evidence under task/results/. A potentially reusable discovery is reported as a candidate; it is not promoted into kb/circuits/ by the same run. This boundary prevents one unusual case from silently changing the rule used by every later case.

General CLI layout

Normal CLI use keeps the KB and task as sibling or otherwise non-overlapping directories. The names do not have to be literally kb and task, because -kbdir and -workdir identify their roles. Relative paths make examples portable from the current directory:

./kb/
  input/          reusable source documents
  circuits/       reviewed reusable SOP
  candidates/     unpromoted learning proposals
  results/        learning reports

./task/
  input/          current request and case data
  sop/            task-specific SOP
  results/        analysis outputs

Run agent -kbdir ./kb when the KB itself is the active workspace and the agent is learning candidate circuits. Run agent -kbdir ./kb -workdir ./task when the agent is analyzing the current task. There is no separate --learn switch: the absence of -workdir selects learning, while its presence selects analysis. The manual CLI tutorial provides commands and expected observations for both modes.

Evaluation layout

An evaluation is a committed reproduction of the same two-workspace arrangement. Keeping both directories below one evalN/ folder makes every input, circuit, and result statically browsable without weakening the boundary:

docs/eval/evalN/
  README.md
  index.html
  kb/
    input/          reusable rules and reference knowledge
    circuits/       reviewed reusable packages named kb.*
  task/
    input/          current evaluation data and request
    sop/            packages named evalN.*
    results/        expected output and report

Package names reinforce the filesystem roles. A reusable evaluation circuit is loaded with prefix kb and called as, for example, kb.policy. Its task root is loaded with prefix eval1 and called as eval1.analysis. A direct deterministic run therefore supplies both roots:

node src/cli.mjs sop run \
  --kb-root ./docs/eval/eval1/kb/circuits \
  --root ./docs/eval/eval1/task/sop \
  --prefix eval1 \
  --package eval1.analysis

The command does not ask the coding agent to reinterpret the Markdown. It executes the already reviewed fixture so the parser, compiler, cross-root package resolution, and semantic output remain deterministic. The evaluation page then places the source knowledge, current task, executable interpretation, and observed result next to one another for inspection. Start with the evaluation catalog and open a case to see the convention applied.

How to classify an ambiguous document

Some documents contain both a durable rule and one-time facts. Split them instead of choosing a misleading folder. For a policy review, place the policy clause in kb/input/rule.md; place employee cases and the requested report fields in task/input/. For a document-consistency review, general comparison rules belong in kb/input/, while the chapters being compared belong in task/input/. The task SOP can call a KB interpreter repeatedly without making those chapters part of the reusable corpus.

A rule may remain task-local when the request explicitly says it applies only to this run. Record that scope in the task source and encode it in task/sop/; do not place it in kb/circuits/ merely because it looks like a rule. Conversely, repetition across several tasks is evidence for a separately reviewed KB candidate, not authority for automatic promotion.
