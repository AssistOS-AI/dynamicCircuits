What Dynamic Circuits can do today

The repository tests whether a coding agent can turn readable task documents into executable SOP circuits, then use a deterministic local runtime to produce inspectable findings and receipts. Eight committed evaluation domains with 24 task runs work now; unrestricted natural-language question answering and automatic discovery of every relevant KB rule do not.

8 domains / 24 runsReasoning, scale, text generation, and independent verification

Planned assuranceAutomatic matching, complete closure, trust profiles, and certificates

What the experiment tests

The project does not train a language model. Codex is an external, already-trained coding agent. “Learning” in this repository means converting source documents into reviewable SOP code under a KB's candidates/ folder. “Analysis” means converting one task's source files into task-local SOP under sop/, executing it, and writing reports under results/. Reusable knowledge and current task data remain separate according to the KB/task directory convention.

The committed datasets under docs/eval/ are evaluation fixtures, not a model-training corpus. They test whether the parser, compiler, runtime, circuit composition, and source-to-code boundary can represent useful reasoning patterns. Agent quality across model versions is not yet benchmarked automatically.

What knowledge is built in

The runtime has no built-in facts about law, science, Socrate, project dates, or document terminology. It knows how to parse and execute SOP graphs. Domain knowledge enters through task documents, reviewed packages under kb/circuits/, or generated task code under workdir/sop/. A newly created KB is empty until source documents are interpreted and a reviewer promotes useful candidates.

Codex may have broad pretrained knowledge, but this project does not count that memory as task evidence. Generated conclusions should be grounded in supplied files or identified KB packages. Eval 4 therefore stores “Socrate is a man” as a source-linked fact in knowledge.sop; the reasoner does not assume it from model memory.

Context reasoning example

Eval 4 implements this exact family. Its input says “Socrate is a man” and “Every man is mortal,” then asks three questions. The coding-agent interpretation is committed as knowledge.sop. A reusable reasoner computes unary-rule closure. It answers the direct man question and the derived mortal question with SUPPORTED, while the philosopher question remains UNKNOWN.

This is adaptation from context, but it is explicit and inspectable: the agent writes facts and rules before the deterministic runtime reasons over them. A live task can use the same workflow by placing context and task documents in work/task/input/. A KB learning run can generalize a useful reasoner into a candidate package.

The table separates a useful current experiment from stronger claims. “Works through Codex” means the repository can prepare the task and verify generated SOP, but the interpretation remains agent-produced and must be reviewed. “Not guaranteed” means a successful explicit graph may still omit an applicable rule. “Not supported” identifies an absent entry path or safety boundary rather than a bad answer.

Try it in three steps

  1. Run npm test to reproduce all five committed evaluation circuits.
  2. Run Eval 4 directly with node src/cli.mjs sop run --kb-root docs/eval/eval4/kb/circuits --root docs/eval/eval4/task/sop --prefix eval4 --package eval4.analysis.
  3. Follow the manual CLI tutorial to copy readable documents into a new workdir, inspect the Codex invocation, and run a live source-to-code experiment.
