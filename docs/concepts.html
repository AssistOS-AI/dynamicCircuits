Concept model

Source files are stored as identified artifacts. Interpretation circuits publish provenance-linked facts. SOP commands transform those facts through immutable wires, and receipts record the executed dependencies and outputs.

Purpose and relationship to the system

This page defines the objects named throughout the CLI, runtime, assurance, and operations documentation. It explains how a source file becomes circuit input, how values move through a circuit, and which record connects a final value back to its source. The runtime page describes the implemented mechanics; the assurance page adds applicability and acceptance rules.

Conceptual model

flowchart LR
  S[Source artifact] --> I[Interpretation]
  I --> F[Facts and claims]
  F --> P[Source provenance]

The first diagram describes interpretation. A source artifact contains bytes plus identity metadata such as media type, origin, digest, locators, access policy, and epoch. Interpretation turns selected source spans into facts or claims. Each published item retains a source locator, so later derivations can identify the exact document evidence. Interpretation may also record uncertainty or conflicting readings.

flowchart LR
  F[Input facts] --> C[Circuit instance]
  C --> V[Derived values]
  V --> G[Checks and goals]
  G --> R[Receipt]

The second diagram describes execution. Input facts enter one circuit instance, commands derive canonical values, and checks or goals evaluate declared conditions over those values. The receipt records the package, instance, executed nodes, input/output hashes, and check outcomes. Child circuits repeat the same structure behind an explicit ordered interface.

The full vocabulary—including attempts, profiles, trust states, receipts, closure, cache entries, artifacts, hooks, and epochs—is normative in DS009.

Example: interpreting a policy date

A policy source states that ordinary notice requires 30 days. Interpretation can publish a fact such as {minimumDays: 30} with a locator to the policy paragraph. A task circuit combines that fact with a case value such as {noticeDays: 10}. Its derived compliance value is false, its goal checks that every case was classified, and its receipt connects the result to both input values and the rule package.

Values, wires, and composition

Values are canonical JSON-like data plus explicit absence and content-addressed artifact references. Local wires are single-assignment: an input or node output defines a wire exactly once. Identity is based on canonical content and producing context, not mutable object identity or filesystem path. Child circuits receive ordered input values and return ordered outputs; their internal wires never leak into the caller.

This SSA model makes dependencies, dead work, parallel opportunities, refusal propagation, hashing, and provenance inspectable. See DS010.

The surface defines what authors write. The command ABI defines how JavaScript receives and returns values. Package and IR rules turn symbolic calls into resolved graph nodes. Core supplies portable deterministic commands. Keeping these contracts separate prevents syntax, runtime behavior, and future assurance policy from becoming one implicit mechanism.

Implemented boundary

The current parser and compiler support explicit ports, JSON string arguments, local JavaScript command descriptors, immutable wires, nested positional circuits, goals and invariants, and parsed matcher metadata. The runtime executes relevant graph slices in a restricted Node VM and emits structured receipts. Semantic indexing, automatic matcher wiring, effects/capability brokers, and rich types are designed but not yet implemented.

The coding agent authors circuit source. The parser, compiler, and runtime determine whether it compiles, which nodes execute, and which receipt is emitted.
