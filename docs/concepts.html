Documentation / How it works

From documents to an executable analysis

The coding agent reads human documents and writes SOP files. The compiler checks the SOP files, the runtime executes them, and the result folder preserves both the report and the execution evidence.

A concrete example

Eval 1 asks whether three notice cases comply with a policy. Its reusable KB input rule.md states the 30-day rule and the 10-day exception. Its current task inputs are cases.md, which supplies facts for cases A–C, and task.md, which states the requested output. These are ordinary Markdown documents. They contain no JSON payload and no hidden runtime instruction.

This diagram is the complete implemented path. The first arrow is an interpretation step performed by the coding agent: prose rules and case facts become explicit commands and values in sop/. The second arrow is a mechanical check performed by local code: package names, arguments, wires, dependencies, outputs, and cycles are validated. The third arrow is deterministic execution: the same accepted SOP and inputs produce the same findings and receipt. The diagnostic branch preserves a precise compile error so the agent or reviewer can repair the SOP before any node executes.

What each file contributes

The following table traces the example instead of assigning vague architectural labels. Each row names a real file, the information taken from it, and where that information appears after interpretation.

The important boundary is visible in the middle column. The agent may misunderstand a document, so its generated SOP must remain inspectable. The runtime does not reread the policy and does not silently repair that interpretation. It executes the rule that was actually written, allowing a reviewer to compare source prose, executable rule, and result. The KB/task convention explains why the policy and cases occupy separate roots.

What the agent writes

For one case, the generated rule has five ordered inputs: case identifier, observed notice days, expedited-request flag, and written-consent flag. Its command converts the notice value to a finite number, validates the two flags, selects the required minimum, and returns fields such as requiredDays, compliant, and reason. The task circuit invokes that reusable rule three times and aggregates the returned findings.

@input caseId noticeDays expeditedRequested writtenConsentRecorded
@output finding

@finding evaluate $caseId $noticeDays $expeditedRequested $writtenConsentRecorded

The snippet is intentionally small, but its interface is meaningful. A caller cannot omit consent evidence without an arity error. Inside the complete file, invalid booleans and non-finite notice values produce classified refusal data. A different task can reuse the same rule by supplying different explicit values instead of copying or editing its internal code.

What the compiler checks

The compiler does not judge whether 30 days is the correct legal policy. It checks whether the executable interpretation is internally well formed:

  • every $wire is produced exactly once before it is consumed;
  • command and child-circuit calls receive the declared number of arguments;
  • public outputs, goals, and invariants are reachable from real graph nodes;
  • package names resolve from file paths without collisions;
  • the dependency graph has no cycle.

For example, removing the consent argument from a call to kb.policy stops compilation with CIRCUIT_ARITY_MISMATCH. Misspelling $noticeDays stops with FREE_WIRE. Neither defect reaches runtime or becomes a polished report.

What the runtime does

The runtime starts from the requested outputs and obligations, walks backward to find the required nodes, and executes those nodes in dependency order. Nodes unrelated to an output or goal are marked dead and do not run. Public outputs contain the requested findings; the receipt separately records node states, input and output hashes, checks, nested calls, and the final outcome.

In Eval 1 the root circuit executes three child calls. Case A fails the 30-day rule, case B uses the 10-day exception, and case C satisfies the ordinary rule. The aggregate output is three cases, two compliant, one violation. The coverage goal passes because three distinct case findings were produced. You can reproduce the exact run from the manual tutorial.

What is not automatic yet

The current agent chooses which KB circuits to inspect and how to connect them to the task. The current runtime then compiles and executes those explicit calls. It does not yet search a semantic registry, prove that every applicable KB rule was selected, run mandatory fixed-point closure, evaluate trust profiles, or issue a final acceptance certificate. Those mechanisms are maintained design work, not claims about the executable release.

This distinction matters during testing. Today you can verify input coverage, inspect generated SOP, rerun circuits, compare outputs, and examine receipts. You cannot infer from one successful run that all rules in an arbitrary corpus were discovered. The assurance page explains how that future coverage check is intended to work, using the same notice example rather than a separate vocabulary.

The normative language and runtime contracts are DS004 and DS005. Use the input guide for source preparation and the manual tutorial for a reproducible run.
