Test the CLI manually

This tutorial verifies the project in increasing order of scope: first the deterministic SOP kernel, then workspace preparation, then a live Codex analysis, and finally KB learning. Every step states its inputs, command, generated files, and expected observation.

What you will test

The kernel test proves that committed SOP code compiles and executes. The workspace test proves that the CLI creates the required directory contract and manifest. The live analysis test asks Codex to transform policy and case documents into task-specific SOP code and reports. The learning test asks Codex to transform source rules into reviewable KB candidates.

The tests are cumulative. If the deterministic tests fail, fix them before interpreting a coding-agent result. Agent output is useful only when the local compiler and runtime used to verify it are working.

Prerequisites

Run the commands from the repository root. Node.js 20 or newer is required. A live agent test also requires the codex CLI to be installed and authenticated through its normal local configuration.

node --version
npm test
node src/cli.mjs help

Expected observation: the test suite passes, and the help output shows learning with only -kbdir and analysis with both -kbdir and -workdir. During repository development the examples use node src/cli.mjs; after package installation the equivalent executable is agent.

1. Run a committed circuit

Eval 1 contains a human-readable notice rule and three cases. Its committed SOP code is the reviewed executable interpretation. Compile the root package first:

node src/cli.mjs sop compile \
  --root ./docs/eval/eval1/sop \
  --prefix eval1 \
  --package eval1.analysis

Expected observation: stdout contains compiled package IR with package name eval1.analysis, two public outputs, three nested calls to eval1.policy, dependencies, goals, and dead-node metadata.

Execute the same package:

node src/cli.mjs sop run \
  --root ./docs/eval/eval1/sop \
  --prefix eval1 \
  --package eval1.analysis

Expected observation: outcome SUCCEEDED; case A is non-compliant; case B is compliant through the expedited exception; case C is ordinarily compliant; statistics are total 3, compliant 2, violations 1. The receipt contains one root circuit, three child policy receipts, node input/output hashes, and a passing goal. Compare it with the checked result summary.

Change one case interactively

Run the reusable policy circuit directly to see how one fact changes the decision. These three calls use the same case identifier and 10 notice days. Only the evidence flags or notice value change:

node src/cli.mjs sop run --root ./docs/eval/eval1/sop --prefix eval1 \
  --package eval1.policy --inputs '["manual","10","false","false"]'

node src/cli.mjs sop run --root ./docs/eval/eval1/sop --prefix eval1 \
  --package eval1.policy --inputs '["manual","10","true","true"]'

node src/cli.mjs sop run --root ./docs/eval/eval1/sop --prefix eval1 \
  --package eval1.policy --inputs '["manual","unknown","true","true"]'

The first call succeeds with compliant: false because the ordinary minimum is 30. The second succeeds with exceptionUsed: true and compliant: true because both exception conditions are present. The third returns REFUSED and no public output because unknown is not a finite notice duration. The quoted array is only the CLI transport for ordered circuit ports; task and KB source documents remain readable text files.

2. Prepare a task

Reuse the eval's Markdown documents as raw agent input, but do not copy its generated sop/ or results/. The new task therefore starts with source material only:

mkdir -p ./work/manual-notice/input ./kb
cp ./docs/eval/eval1/input/*.md ./work/manual-notice/input/
node src/cli.mjs prepare \
  -kbdir ./kb \
  -workdir ./work/manual-notice

Expected observation: the CLI prints a workspace manifest with mode analyze. Inspect these paths:

  • work/manual-notice/.dynamic-circuits/input-manifest.json lists all three Markdown inputs with hashes.
  • work/manual-notice/sop/ and results/ exist and are initially empty.
  • work/manual-notice/circuitSkills and .agents/skills resolve to the maintained project skills.
  • work/manual-notice/AGENTS.md explains input coverage, read-only KB access, and output locations.

3. Inspect the agent call

Dry-run prepares the same workspace and prints the external process arguments and prompt without starting Codex:

node src/cli.mjs \
  -kbdir ./kb \
  -workdir ./work/manual-notice \
  -agent codex \
  --dry-run

Expected observation: command codex, current directory work/manual-notice, workspace-write sandbox arguments, prompt delivery through standard input, and a prompt that requires all manifest files, SOP output under sop/, reports under results/, and read-only KB use.

4. Run Codex

Run the same invocation without --dry-run:

node src/cli.mjs \
  -kbdir ./kb \
  -workdir ./work/manual-notice \
  -agent codex

After completion, inspect the task in this order:

  1. Open results/agent-summary.md. It should account for every input, list generated and reused circuits, report execution outcomes, and state limitations.
  2. Inspect every file under sop/. Policy values and case facts should appear as executable circuit logic or explicit inputs, not as claims that were never compiled.
  3. Follow the compile and run commands recorded by the agent. Every conclusion supported by a circuit should have a successful or explicitly classified runtime result.
  4. Compare the generated classification with eval 1. Differences should be explained by a different interpretation, a refusal, or an implementation error—not silently ignored.
  5. Inspect .dynamic-circuits/last-run.json for adapter, mode, working directory, prompt digest, timestamps, exit status, and signal.

A useful run produces grounded reports plus executable SOP code that can be compiled again. A report with no input coverage, no circuit execution evidence, or hidden source assumptions is incomplete even when the prose sounds plausible.

5. Learn a KB rule

Learning uses no workdir. Copy only reusable source material into the KB input directory:

mkdir -p ./kb/input
cp ./docs/eval/eval1/input/rule.md ./kb/input/notice-rule.md
node src/cli.mjs -kbdir ./kb -agent codex --dry-run
node src/cli.mjs -kbdir ./kb -agent codex

Expected observation: mode learn and KB as the agent current directory. The agent reads input/ and reviewed circuits/, writes proposals only under candidates/, and writes results/learning-summary.md. Trusted circuits/ remains unchanged. Inspect each candidate for source provenance, applicability, inputs/outputs, exceptions, refusal behavior, tests, assumptions, and review requirements.

Useful inputs

The CLI inventories every regular file, but the external coding agent determines which formats it can interpret. Start with UTF-8 Markdown or text because rules, assumptions, and source identity remain easy to review. CSV and source-code files are also practical when their meaning is documented. PDF, image, archive, or proprietary formats depend on the selected agent's local tools and should be recorded as unsupported when they cannot be inspected.

Input setWhat to includeUseful generated circuitResult to inspect
Policy applicationRule, exceptions, priorities, cases, requested fieldsRule circuit plus task rootPer-case findings, aggregate counts, refusal cases
Scientific claimClaim, observation table, validity rule, requested witnessDataset interpretation plus verifierVerdict, witness, statistic, grounding goal
Document consistencySeveral chapters, term/date rules, source labelsPer-document interpreter plus synthesisConflicts with source attribution
Technical reviewRequirements, configuration, implementation files, acceptance criteriaRequirement checks and coverage rootPassed, failed, missing, and unsupported requirements

The table pairs source structure with an executable output shape. Good tasks state which documents are authoritative, which rules contain exceptions, what counts as missing evidence, and which fields the final report must contain. The coding agent can then encode those decisions explicitly instead of guessing them from an underspecified prompt.

Current limits

The current runtime executes explicit circuit calls, local checks and goals, nested packages, canonical values, and receipts. Semantic registry search, automatic matcher wiring, mandatory closure, assurance profiles, trust evaluation, persistent caching, final certificates, and hardened multi-tenant isolation remain planned. A useful current test should evaluate workspace preparation, coding-agent transformation, explicit SOP execution, and report grounding; it should not expect the planned Assurance Core to run automatically.

Maintenance checklist

When CLI behavior or the underlying theory changes, update this tutorial together with the implementation:

  • Keep commands aligned with current option names and inferred modes.
  • Keep copied sample inputs aligned with the evaluation source documents.
  • Update expected folders, manifest fields, runtime outcomes, and result values.
  • Update the input guidance when new document or artifact support becomes executable.
  • Run npm run check and the static-site verifier after every tutorial change.
