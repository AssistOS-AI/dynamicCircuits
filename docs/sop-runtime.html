Documentation / SOP runtime

A small executable circuit kernel

The reference implementation preserves the stable syntax decisions from the historical design while limiting its claims to parser, compiler, and local execution behavior covered by tests.

Authoring surface

@input left right
@output total

@add define left right
    function run({ left, right }) { return left + right }
    function check({ left, right }, output) { return output === left + right }
    return { run, check }

@total add $left $right

Ports and calls are positional. String literals are JSON strings. Commands return one value; circuits may expose multiple ordered outputs. Wires are local and immutable, and nested circuits exchange values only through their declared interfaces.

Compilation and execution

flowchart LR
      F[.sop files] --> G[Package registry]
      G --> P[Parser]
      P --> C[Compiler]
      C --> V{SSA, arity,
      coverage, cycles}
      V -->|valid| E[Slice executor]
      V -->|invalid| D[Structured diagnostic]
      E --> X[Structured receipt]

The compiler resolves core, local, qualified, and nested circuit calls. It marks dead nodes outside output and assurance slices. The executor distinguishes success, refusal, rejection, and error; failed child circuits do not leak partial public outputs.

agent sop compile --root ./sop --package analysis
agent sop run --root ./sop --package analysis --inputs '["4","7"]'

Isolation boundary

Command code runs in a Node vm context without process, filesystem, network, module loading, clocks, randomness, or oracle services. String and WebAssembly code generation are disabled and synchronous execution has a timeout. This is a development guard for reviewable code, not a production sandbox for hostile multi-tenant programs.

The runtime parses matcher metadata but does not yet execute semantic indexes, mandatory matchers, closure, persistent caches, trust profiles, or external effects. The exact current contract is in DS005.
