SOP compiler and runtime

The parser reads SOP files, the compiler resolves packages and builds an immutable dependency graph, and the runtime executes the required graph slice and emits structured receipts.

Purpose and relationship to task analysis

A coding agent can interpret a document in many ways, so Dynamic Circuits stores the calculations and checks that support a conclusion as SOP source. The compiler turns that source into a graph with explicit producers and consumers. The runtime then evaluates the graph independently of the coding agent. This page explains the implemented language subset and execution path; the concept model defines its broader vocabulary, and the assurance page describes planned acceptance checks above the runtime.

Authoring surface

@input left right
@output total

@add define left right
    function run({ left, right }) { return left + right }
    function check({ left, right }, output) { return output === left + right }
    return { run, check }

    @total add $left $right

The example defines a circuit with two ordered inputs and one ordered output. The local add command receives an object whose keys match the declared formals, returns their sum, and checks the returned value. The final line creates wire total by passing the input wires to that command. The compiler rejects a missing wire, duplicate wire, surplus argument, or undeclared output before execution.

Ports and calls are positional. String literals are JSON strings. Commands return one value; circuits may expose multiple ordered outputs. Wires are local and immutable, and nested circuits exchange values only through their declared interfaces. Arrays and plain objects returned from a command's VM realm are normalized into host canonical values before they are frozen and hashed.

Compilation and execution

Compilation

flowchart LR
      F[SOP files] --> P[Parser]
      P --> C[Compiler]
      C -->|valid| G[Dependency graph]
      C -->|invalid| D[Diagnostic]

The compilation diagram has two possible results. Valid source becomes a dependency graph whose nodes contain resolved callees, arguments, outputs, dependencies, and source locations. Invalid source stops before runtime and returns a diagnostic such as FREE_WIRE, CIRCUIT_ARITY_MISMATCH, or GRAPH_CYCLE.

Execution

flowchart LR
      G[Dependency graph] --> S[Required slice]
      S --> E[Execute nodes]
      E --> R[Outputs and receipt]

The execution diagram begins with the validated graph. The runtime selects nodes required by public outputs, goals, and invariants; nodes outside that slice are recorded as dead and remain unexecuted. Required nodes run in topological order. The result contains public outputs only after successful execution and always includes the corresponding receipt.

The executor distinguishes success, refusal, rejection, and error. A refusal represents an unmet command precondition; rejection represents a failed check, goal, or invariant; error represents an execution failure. A failed child circuit contributes its child receipt to the parent failure and exposes no partial child outputs.

The commands below compile package analysis from ./sop and then run it with two string values. The JSON printed by run contains the outcome, ordered outputs, and receipt:

agent sop compile --root ./sop --package analysis
agent sop run --root ./sop --package analysis --inputs '["4","7"]'

Isolation boundary

Command code runs in a Node vm context. The context omits process, filesystem, network, module loading, clocks, randomness, and oracle services. String and WebAssembly code generation are disabled, and synchronous execution has a timeout. Production execution of hostile multi-tenant code requires process-level memory, CPU, and operating-system isolation that this runtime does not implement.

Current runtime scope: explicit circuit calls, local checks and invariants, canonical values, and receipts. Planned scope: semantic indexes, mandatory matchers, closure, persistent caches, trust profiles, and mediated effects. See DS005.

For example, a coding agent may convert a policy paragraph into a command that calculates a deadline from explicit date and rule inputs. The command cannot open the policy file itself, read a secret from the environment, or call a web service. Required data must enter through circuit inputs or generated SOP source; future effectful operations must use explicit capability brokers defined by the security architecture.
