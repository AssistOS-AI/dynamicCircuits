Documentation / Coverage and acceptance

How the system will check that an analysis is complete

The current runtime can prove that selected circuits executed. The planned assurance layer additionally checks whether every applicable rule was selected and whether the available evidence is sufficient to publish the result.

The gap in the current release

Suppose the KB contains an ordinary 30-day notice rule and a 10-day exception that requires both an expedited request and written consent. A coding agent can call both circuits correctly, call only the ordinary rule, or fail to notice the exception. The compiler detects malformed calls, but it cannot currently detect an applicable rule that is never called. A successful receipt therefore means “this explicit graph ran successfully,” not “the KB was searched completely.”

The planned assurance layer closes that gap in four concrete stages: publish task facts, enumerate candidate rules, run deterministic applicability checks, and compare all expected rule instances with the instances that executed.

1. Publish facts

The task interpreter publishes facts with source provenance. For case B in Eval 1 those facts would include the case identifier, 10 notice days, an expedited request, and recorded written consent. Each fact points back to the row or paragraph from which it was interpreted. The semantic index stores these typed facts; it does not store a vague natural language summary as proof of applicability.

2. Find possible rules

flowchart LR
      F[Case B facts] --> Q[Registry query]
      Q --> B[30-day rule]
      Q --> E[10-day exception]

The query uses declared metadata such as fact families, domain, version, jurisdiction, and required inputs. Similarity search may help propose candidates, but it cannot decide applicability. In this example the query returns both notice packages because both consume notice-case facts. The receipt records which registry snapshot and shard were searched, so a later audit can identify the candidate population.

3. Check applicability

Each candidate has a deterministic matcher. The base-rule matcher returns MATCH for every complete notice case. The exception matcher returns MATCH for case B because both required flags are true, NO_MATCH for a case with no expedited request, and UNKNOWN when consent evidence is missing. A match also returns the exact bindings used to instantiate the rule.

Matcher resultMeaning in this projectNext action
MATCHThe declared prerequisites are present and satisfy the matcher.Create a stable rule instance and execute it.
NO_MATCHThe prerequisites are known and the rule does not apply.Record the reason; create no instance.
UNKNOWNA required fact or trusted interpretation is missing.Record the missing prerequisite; a strict run cannot claim complete coverage.

The three states prevent missing evidence from being treated as a negative result. For example, “no consent document was supplied” is not automatically the same fact as “consent was not recorded.” The matcher must state which one it needs and return UNKNOWN when the source cannot establish it.

4. Repeat until nothing new appears

flowchart LR
      M[Matched instances] --> X[Execute rules]
      X --> N[Publish new facts]
      N --> M

Some rules derive facts that activate other rules. The system therefore executes matched instances, indexes their new facts, and reruns mandatory matchers. It stops only when a complete round creates no new facts or instances. Stable instance keys suppress duplicates, and configured round or instance limits turn the result into INCONCLUSIVE instead of silently truncating the analysis.

For the notice example, executing the exception may publish “required notice = 10 days.” That new fact feeds the compliance circuit. Once the compliance finding adds no new applicable rule, closure has reached a fixed point.

5. Compare expected and executed work

After closure, an audit compares every expected instance key produced by matchers with every executed instance key. If the exception matched case B but no corresponding execution receipt exists, the analysis is incomplete even if the base rule succeeded. This is the planned mechanical check for the omission that the current release cannot detect.

6. Decide whether to publish

Publication is a sequence of explicit gates, not one generic boolean:

  1. source and SOP compilation succeeded;
  2. required nodes completed without refusal, error, or blocked dependency;
  3. mandatory matching reached a complete fixed point;
  4. blocking checks and invariants passed;
  5. declared goals were checked by verifiers allowed by the active profile;
  6. package trust, capabilities, conflicts, and budgets satisfied that profile;
  7. the final receipt contains the evidence required for publication.

A malformed execution is ERROR. An unmet command precondition is REFUSED. A false required proposition is REJECTED. Missing evidence, unknown applicability, or an exhausted coverage budget is INCONCLUSIVE. Only a run passing every configured gate is ACCEPTED. These labels tell the user what must change: code, input evidence, a false claim, or a policy decision.

What can be tested today

The repository currently implements compilation, explicit nested calls, relevant-node execution, local command checks, goals and invariants, classified runtime outcomes, canonical values, and nested receipts. Eval 1 demonstrates those mechanics but commits the coding agent's circuit selection in advance. Semantic registry queries, tri-state matchers, mandatory closure, trust profiles, independent verifier policy, and final acceptance certificates remain planned.

During a manual test, inspect whether the agent accounted for every input and whether the generated SOP calls the rules you expect. Treat that review as a temporary human coverage check. The planned mechanism above is intended to turn the same question into receipt-backed executable work. Normative details remain in DS015, DS016, and DS017.
