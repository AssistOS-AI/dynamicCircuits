Documentation / Coverage and acceptance

Coverage now, trusted acceptance later

The current executor proves that every instance returned by its loaded reviewed mandatory matcher registry executed to a fixed point. Planned assurance adds trusted registry selection, richer unknown states, goal policy, and final acceptance certificates.

The implemented boundary

Suppose the KB contains an ordinary 30-day notice rule and a 10-day exception that requires both an expedited request and written consent. A coding agent can call both circuits correctly, call only the ordinary rule, or fail to notice the exception. Explicit task calls still rely on the author's selection. A reviewed mandatory matcher removes that reliance: task SOP publishes a notice value, the matcher returns its binding, and the executor runs the target automatically.

The resulting coverage claim is deliberately scoped. It says the loaded matcher registry was searched completely over explicit semantic publications. It cannot detect a policy that was never encoded as a matcher, prove that Codex interpreted every sentence, or decide that the registry is trusted by an organization. The current and planned stages below keep those different claims separate.

1. Publish facts

The task interpreter publishes facts with source provenance. For case B in Eval 1 those facts would include the case identifier, 10 notice days, an expedited request, and recorded written consent. Each fact points back to the row or paragraph from which it was interpreted. The semantic index stores these typed facts; it does not store a vague natural language summary as proof of applicability.

2. Find possible rules

The current query uses exact dotted semantic keys such as order.raw. It loads all reviewed mandatory kb.* matchers and commits their code plus apply-target hashes to one registry identity. Domain, version, jurisdiction, sharding, and similarity ranking remain planned retrieval layers. Similarity may eventually propose candidates, but it cannot establish a mandatory binding.

3. Check applicability

Each current matcher returns a complete list of publication-handle tuples. Each tuple is a match; an empty list means no current match. A matcher failure produces INCONCLUSIVE, never a silent no-match. The broader tri-state design below remains useful for future predicates that can distinguish proven non-applicability from missing evidence.

Matcher resultMeaning in this projectNext action
MATCHThe declared prerequisites are present and satisfy the matcher.Create a stable rule instance and execute it.
NO_MATCHThe prerequisites are known and the rule does not apply.Record the reason; create no instance.
UNKNOWNA required fact or trusted interpretation is missing.Record the missing prerequisite; a strict run cannot claim complete coverage.

The three states prevent missing evidence from being treated as a negative result. For example, “no consent document was supplied” is not automatically the same fact as “consent was not recorded.” The matcher must state which one it needs and return UNKNOWN when the source cannot establish it.

4. Repeat until nothing new appears

Some rules derive facts that activate other rules. The system therefore executes matched instances, indexes their new facts, and reruns mandatory matchers. It stops only when a complete round creates no new facts or instances. Stable instance keys suppress duplicates, and configured round or instance limits turn the result into INCONCLUSIVE instead of silently truncating the analysis.

For the notice example, executing the exception may publish “required notice = 10 days.” That new fact feeds the compliance circuit. Once the compliance finding adds no new applicable rule, closure has reached a fixed point.

5. Compare expected and executed work

After closure, an audit compares every expected instance key produced by matchers with every executed instance key. If the exception matched case B but no corresponding execution receipt exists, the analysis is incomplete even if the base rule succeeded. This expected-versus-executed comparison is implemented in the closure receipt.

6. Decide whether to publish

Publication is a sequence of explicit gates, not one generic boolean:

  1. source and SOP compilation succeeded;
  2. required nodes completed without refusal, error, or blocked dependency;
  3. mandatory matching reached a complete fixed point;
  4. blocking checks and invariants passed;
  5. declared goals were checked by verifiers allowed by the active profile;
  6. package trust, capabilities, conflicts, and budgets satisfied that profile;
  7. the final receipt contains the evidence required for publication.

A malformed execution is ERROR. An unmet command precondition is REFUSED. A false required proposition is REJECTED. Missing evidence, unknown applicability, or an exhausted coverage budget is INCONCLUSIVE. Only a run passing every configured gate is ACCEPTED. These labels tell the user what must change: code, input evidence, a false claim, or a policy decision.

What can be tested today

The repository implements compilation, explicit nested calls, relevant-node execution, local checks/goals/invariants, exact-key publications, restricted reviewed matchers, duplicate-safe fixed-point closure, classified outcomes, and closure receipts. Eval 9 selects different subsets from ten mandatory matchers. Eval 10 proves that target publications activate later rules.

Human review is still required for source interpretation, matcher promotion, and the completeness of the KB itself. Profiles, trust thresholds, explicit unknown applicability records, independent verifier policy, and final acceptance certificates remain planned. Read the implemented convention before the normative details in DS015, DS016, and DS017.
