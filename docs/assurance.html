Assurance model

Assurance evaluates whether applicable rules were executed, required checks and goals passed, trust and budget policies were satisfied, and the final receipt contains the evidence required by the active profile.

Purpose and relationship to execution

The SOP runtime answers a technical question: did the selected graph execute, refuse, fail a check, or raise an error? Assurance answers a broader task question: were all declared applicable rules selected, were the required verifiers trusted, were conflicts and resource limits handled according to policy, and is the evidence sufficient for publication?

This page explains the planned layer above the current runtime. The concept page defines facts, templates, and receipts. The operations page explains how evidence, cache state, and capability decisions are stored. The current implementation boundary is stated at the end of this page.

Discovery, verification, and closure

flowchart LR
  F[Semantic facts] --> D[Candidate search]
  D --> M[Deterministic matcher]
  M -->|MATCH| I[Template instance]
  M -->|NO MATCH or UNKNOWN| O[Recorded outcome]

The first diagram separates retrieval from applicability. Candidate search uses metadata or approximate similarity to find plausible templates. A deterministic matcher examines semantic facts and returns MATCH with bindings, NO_MATCH with a reason, or UNKNOWN with missing prerequisites. Only MATCH creates a template instance.

flowchart LR
  F[New facts] --> M[Mandatory matchers]
  M --> I[New instances]
  I --> C[Fixed point]
  C --> A[Expected/executed audit]

The second diagram shows mandatory closure. New facts activate the mandatory matchers registered for those fact families. Matches create new instances, and instance outputs may publish more facts. The cycle ends when one complete round adds nothing. The final audit compares all expected instance keys with the instances that actually executed; an unresolved matcher or configured limit produces INCONCLUSIVE. See DS015 and DS016.

Example: ordinary rule and exception

A notice-period task publishes the ordinary 30-day rule, case facts, and evidence of written consent. Candidate search finds both the base rule and expedited exception. Deterministic matchers bind the base rule to every case and the exception only to the case with consent. Closure audits that all expected case/rule combinations executed before acceptance proceeds.

Seven acceptance gates

  1. Compilation and static validation succeed.
  2. Required execution has no refusal, error, or blocked dependency.
  3. Mandatory closure reaches a verified fixed point.
  4. Blocking checks and invariants pass.
  5. Every goal is verified by an allowed verifier.
  6. Trust, capability, budget, conflict, and profile policies pass.
  7. The final receipt is complete, canonical, and publishable.

The classified alternatives are deliberate: malformed execution is ERROR; unmet preconditions are REFUSED; false obligations are REJECTED; unresolved evidence or exhausted budgets are INCONCLUSIVE; only every-gate success is ACCEPTED. Full contracts are in DS017.

flowchart LR
  E[Execution evidence] --> C[Closure and checks]
  C --> P[Trust and policy]
  P --> R[Final receipt]

The acceptance diagram groups the seven gates into three stages. Execution evidence supplies node and circuit outcomes. Closure and checks establish coverage and local obligations. Trust and policy evaluate allowed packages, capabilities, budgets, conflicts, and goal verifiers. A final receipt is publishable only after all three stages pass.

Conditional correctness and trust

An acceptance certificate means the declared computation followed the identified sources, code, rules, profile, registry, and environment. It remains conditional on source authenticity and completeness, command semantics, matcher coverage, verifier correctness, runtime integrity, and oracle behavior. Trust is versioned and scoped: UNTRUSTED, CANDIDATE, REVIEWED, VERIFIED, or REVOKED.

Parser, compiler, scheduler, canonicalizer, capability enforcement, Assurance Core, and selected verifiers form the trusted computing base. Coding agents, approximate retrieval, candidate circuits, and a command's own confidence are outside it. High-assurance profiles need independent checks, redundant implementations, certificate verifiers, signatures, or audits. See DS018.

Current implementation

The current runtime implements checks, invariants, refusal/rejection/error separation, nested receipts, canonical values, and deterministic graph execution. Profiles, semantic matchers, mandatory closure, trust registries, independent goal verifiers, and acceptance certificates are normative future work. Current evals therefore report runtime outcome and semantic verdict separately.
