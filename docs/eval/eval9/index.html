Eval 9: Mandatory registry coverage

Ten reviewed matchers share one evaluator. Each task publishes only its current control records; the executor discovers and runs every matching obligation without direct KB calls in task SOP.

What this evaluation proves

The three tasks activate different subsets of a ten-rule registry: four, three, and four instances. This separates applicability from execution. A dotted semantic key identifies a current fact family, a reviewed mandatory matcher converts every publication in that family into a binding, and @apply names the reusable rule that must run.

Open a task's generated analysis.sop and compare it with its executor report. The task circuit publishes facts but does not call kb.mandatory_controls.evaluate. The report's closure table records the registry size, expected instances, executed instances, and missing instances. A finding with compliant: false remains a successful rule result; it is not confused with runtime failure.

The file tree keeps KB source, reviewed KB circuits, task input, generated task SOP, executor-owned output, and evaluator evidence in separate branches. The convention is explained in Mandatory rules and closure; the normative contracts are DS015 and DS016.
