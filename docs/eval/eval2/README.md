# Eval 2: Universal claim and counterexample

## Evaluation question

Can the system keep a positive mean separate from a universal claim and retain the first grounded counterexample?

## What was actually executed

This case uses two separate workspaces. Human-readable reusable material is under `kb/input/`. A real Codex learning run
generated review-required candidates under `kb/candidates/`; only the reviewed SOP files were promoted to
`kb/circuits/`. Human-readable current evidence and the request are under `task/input/`. A separate real Codex analysis
run generated task-local packages under `task/sop/task/`, including the fixed no-input root `task.analysis`.

After Codex exited, the Dynamic Circuits CLI registered the reviewed KB with prefix `kb`, executed `task.analysis`, and
wrote `task/results/runtime-result.md` directly from public outputs and the receipt. Codex did not author that result.
`task/results/agent-summary.md` is only a provenance journal and has no result authority.

## Scale and observed result

Complexity: 1 KB source, 1 reviewed KB package, 3 task inputs, 4 generated task packages, 8 observations.

Observed executor result: SUCCEEDED. Verdict REFUTED; first witness observation-4 = -2; mean 5.25; all eight observations retained.

The source-derived expectation and comparison are in `expected.md`. That file is outside both input trees and the coding
agent is instructed not to inspect it. Eval 6 retains both the original expectation and the correction justified by the
independent verifier.

## Three independent task runs

| Run | Human input | Observed executor result |
| --- | --- | --- |
| Task 1 | Mixed observations with a later negative witness | `SUCCEEDED`; `REFUTED`, mean 5.25 |
| Task 2 | Four positive observations | `SUCCEEDED`; `SUPPORTED`, no witness, mean 2.5 |
| Task 3 | Zero followed by mixed observations | `SUCCEEDED`; `REFUTED` by Z1, mean 3.5 |

The three inputs are separate Markdown datasets. Each has separately generated SOP and a separately rendered receipt-backed
result; the KB reviewer is the only reusable circuit shared by the runs.

## Artifact groups

- `kb/input/`: reusable human-readable source only.
- `kb/candidates/`: Codex learning artifacts, tests, and provenance; not trusted automatically.
- `kb/circuits/`: reviewed executable KB SOP only.
- `task/input/`, `task2/input/`, `task3/input/`: three distinct human-readable task sources.
- `taskN/sop/task/`: Codex-generated executable representation for that run and its `task.analysis`.
- `taskN/results/runtime-result.md`: authoritative executor output for that run.
- `taskN/results/agent-summary.md`: non-authoritative coding-agent provenance for that run.
- `expected.md`, `task2/expected.md`, and `task3/expected.md`: post-run expectations, never semantic input.
- `../eval-manifests.js` and `../eval-file-tree.js`: the shared hierarchy, explanations, and reusable tree component used by every evaluation page.

The HTML file browser keeps these groups distinct; it never labels a source document and a generated circuit as the same
kind of artifact.

## Reproduce the circuit without invoking Codex

From the repository root:

```sh
node src/cli.mjs sop compile \
  --kb-root ./docs/eval/eval2/kb/circuits \
  --root ./docs/eval/eval2/task/sop \
  --package task.analysis

node src/cli.mjs sop run \
  --kb-root ./docs/eval/eval2/kb/circuits \
  --root ./docs/eval/eval2/task/sop \
  --package task.analysis
```

These commands print structured runtime data. The committed Markdown report is generated by the same executor through the
workspace CLI, and its package/output/receipt hashes identify the exact run.

## Limitations

The claim is dataset-scoped. The circuit does not infer a population result or validate measurement provenance.

A successful runtime outcome proves that the explicit generated graph executed and its assurance declarations passed. It
does not by itself prove that the coding agent interpreted the source correctly; the source, generated SOP, candidate tests,
expectation comparison, and executor receipt remain separately inspectable.
