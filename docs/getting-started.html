Understand the project in ten minutes

Dynamic Circuits gives a coding agent a folder of documents, asks it to write executable analysis code, and uses a local compiler and runtime to check and run that code. This page explains the pieces without assuming knowledge of SOP Lang.

The practical problem

A coding agent can read a policy and write a convincing answer, but prose alone does not show exactly which rule was applied to which facts. It is difficult to rerun one calculation, detect an omitted case, or distinguish a failed precondition from a false conclusion. This project makes the agent leave an executable representation of the analysis next to the report.

The user supplies readable source files. Codex, or another configured coding agent, interprets them and authors SOP files. Local project code parses those SOP files, checks their dependency graph, runs required commands, and emits outputs plus a receipt. The report can then refer to work that another user can execute again.

The four moving parts

PartWhat it doesWhat it does not do
User documentsState policies, evidence, cases, datasets, review rules, and requested output.They do not need to contain JSON or SOP syntax.
Coding agentReads documents and writes task-value SOP plus a larger root that calls optional KB packages or publishes values for mandatory matchers.It does not own the official result or become part of deterministic circuit execution.
SOP kernelParses, compiles, executes explicit calls, closes loaded mandatory matcher instances, and renders classified outputs plus receipts.It does not reinterpret original prose or invent an absent matcher.
Filesystem contractSeparates persistent KB knowledge from one task's inputs, generated code, and results.It does not automatically promote generated candidates to trusted knowledge.

The separation is deliberate. The coding agent handles document understanding and code generation. The kernel handles repeatable graph mechanics. A reviewer can compare both: “Did the agent encode the document correctly?” and “Did the encoded graph execute correctly?” are different questions and have different evidence.

One example from source to answer

A source policy says that normal notice is 30 days. It also says that 10 days is enough when expedited treatment was requested and written consent was recorded. A case table contains three rows. The requested task asks for one finding per row and aggregate totals.

At the first arrow, Codex's interpretation is split by lifetime: reusable policy belongs in reviewed KB SOP, while current cases and the requested output become task-value SOP. A larger task root connects the two. At the second arrow, the local runtime calls the policy once for each case and returns structured findings. At the third arrow, the result folder preserves the executor-owned Markdown result and an optional agent provenance journal. Open Eval 1 to inspect the source, generated code, and result side by side.

Two CLI modes

Learning and analysis are selected by directory arguments, not by a separate learn switch:

# Learn reusable knowledge from kb/input/
node src/cli.mjs -kbdir ./kb -agent codex

# Analyze one task from work/case-17/input/
node src/cli.mjs -kbdir ./kb -workdir ./work/case-17 -agent codex

The first command runs in the KB and may write proposals under candidates/. The second runs in the task folder and may write sop/ and results/; it reads reviewed KB circuits without modifying them. Use --dry-run to inspect the prepared process and prompt without starting Codex.

What a successful current run proves

A successful current run proves that the generated SOP was syntactically valid, package and wire references resolved, required graph nodes completed, and declared local checks or goals passed. Its receipt identifies the graph execution behind the public values. This is already useful for rerunning calculations and exposing agent assumptions as code.

When task SOP publishes exact semantic keys, the current closure receipt also proves that every binding returned by the loaded reviewed mandatory matcher registry executed. It does not prove that Codex interpreted every source fact, that the KB contains every real-world rule, or that an external trust profile accepts the registry. Richer discovery, persistent evidence, trust profiles, and final certificates remain planned. See Mandatory rules and closure for a complete example.
