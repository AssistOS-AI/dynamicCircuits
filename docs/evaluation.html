Documentation / Evaluation

Tests and evaluation cases

Unit tests cover the parser, compiler, runtime, CLI, workspace preparation, agent adapters, documentation links, and historical integrity. Five evaluation workspaces execute policy, scientific, cross-document, contextual-reasoning, and large 10 × 10 composition cases against committed inputs.

Purpose and relationship to the system

The project has two verification levels. Unit tests isolate one contract, such as free-wire detection or workspace symlink creation. Evaluation cases combine source documents, multiple circuit packages, goals, expected outputs, and reports in the same directory shape used by a task. Together they show whether the implementation primitives work individually and whether they compose into a meaningful analysis.

The evaluation fixtures currently validate deterministic circuit behavior. They provide reference material for future coding-agent benchmarks, but they do not claim that a particular agent version independently recreated each circuit from the prose sources.

Evaluation cases

Each case reproduces two workspaces. kb/input/ stores reusable rules or reference knowledge and kb/circuits/ stores their reviewed executable packages. task/input/ stores the current dataset and request, task/sop/ stores the task-specific interpretation and wiring, and task/results/ stores the checked machine summary and human report. README.md states the evaluation question, reproduction command, observed result, complexity, and limitations. See the KB/task convention for the classification rule and package namespaces.

The five rows exercise different failure risks. Eval 1 checks that an exception does not replace the base rule for unrelated cases. Eval 2 checks that an aggregate statistic does not answer a universal claim. Eval 3 checks that repeated interpretation and synthesis preserve incompatible source claims. Eval 4 checks direct evidence, rule-derived evidence, and open-world unknown behavior after coding-agent interpretation. Eval 5 checks real source-to-SOP learning, reviewed promotion, real task-to-SOP interpretation, 10 repeated review instances, 100 nested rule instances, and exact aggregate coverage. Open the evaluation catalog, choose one evaluation, then select any source, circuit, review record, or report in that case's two-pane view.

Runtime SUCCEEDED means the circuit completed and its local goals passed. The domain result can still be a violation, a refuted claim, or an unresolved conflict; each case therefore states runtime outcome, semantic result, and scope limit separately.

Historical integrity

The original design package remains an immutable baseline. Initialization and later migrations must compare its aggregate file hash before and after work. Current requirements live in the contiguous DS set and must be regenerated into the specification matrix.
