Documentation / Evaluation

Tests and evaluation cases

Unit tests cover the deterministic implementation. Ten evaluation domains add 30 real task workspaces spanning policy, scientific claims, document consistency, contextual reasoning, large governance review, three generator–verifier families, and mandatory closure.

Purpose and relationship to the system

The project has two verification levels. Unit tests isolate one contract, such as free-wire detection or workspace symlink creation. Evaluation cases combine source documents, multiple circuit packages, goals, expected outputs, and reports in the same directory shape used by a task. Together they show whether the implementation primitives work individually and whether they compose into a meaningful analysis.

The committed fixtures validate deterministic circuit behavior and also retain real Codex authoring provenance. Codex generated each task's SOP from that task's readable input and the reviewed KB; after it exited, the CLI executed the fixed root and rendered the official result. Re-running committed SOP is deterministic. Re-generating it with a future agent version is a separate benchmark and may produce different, reviewable code.

Evaluation cases

Each domain contains one KB and three task workspaces. kb/input/ stores reusable rules or reference knowledge and kb/circuits/ stores reviewed executable packages. Each taskN/input/ stores one distinct current dataset or brief, taskN/sop/ stores only that task's generated interpretation and wiring, and taskN/results/runtime-result.md stores the executor-owned output. README.md states the evaluation question, reproduction command, observed result, complexity, and limitations. See the KB/task convention for the classification rule and package namespaces.

The ten rows exercise different failure risks across three runs each. Eval 1 checks that an exception does not replace the base rule for unrelated cases. Eval 2 checks that an aggregate statistic does not answer a universal claim. Eval 3 checks that repeated interpretation and synthesis preserve incompatible source claims. Eval 4 checks direct evidence, rule-derived evidence, and open-world unknown behavior after coding-agent interpretation. Eval 5 checks real source-to-SOP learning, reviewed promotion, real task-to-SOP interpretation, 10 repeated review instances, 100 nested rule instances, refusal, and boundary coverage. Eval 6–8 verify generated prose through separate circuits rather than trusting the generator. Eval 9 verifies complete subset discovery in a ten-matcher registry. Eval 10 verifies branching closure across rounds. Open the evaluation catalog, choose one evaluation, then select any source, circuit, review record, or report in that case's two-pane view.

Runtime SUCCEEDED means the circuit completed and its local goals passed. The domain result can still be a violation, a refuted claim, or an unresolved conflict; each case therefore states runtime outcome, semantic result, and scope limit separately.

Historical integrity

The original design package remains an immutable baseline. Initialization and later migrations must compare its aggregate file hash before and after work. Current requirements live in the contiguous DS set and must be regenerated into the specification matrix.
